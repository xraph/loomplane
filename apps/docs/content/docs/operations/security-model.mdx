Loomplane holds credentials to your clouds and deploys code to them, so it's worth knowing exactly what it protects, how, and what it leaves to you. To report a vulnerability, see `SECURITY.md` in the repository.

## Who can do what

Everything belongs to an organization, and every request acts in one. The organization comes from the signed-in session or the API key, and nothing in the request can change it. Another organization's projects, plans, deployments, connections, variables and keys aren't found, the same answer as something that doesn't exist, so an ID never confirms anything.

Roles are checked on every action. Approving is the line that matters: a developer can plan anything, and only an admin's approval of the exact revision they reviewed changes a cloud. An approval of a plan whose world changed since comes back stale. [Roles and permissions](/docs/reference/roles-and-permissions) has the full list.

An API key acts as the member who made it, with their role, and never more. A read-only key fails every permission that isn't a read, keys can't manage keys, and they lose rights when a member loses a role. Every key expires within a year. Keysmith stores a hash, and the key shows once.

## Where secrets live

| What | Where | Who can read it back |
|---|---|---|
| Cloud credentials | Vault, encrypted with a key derived from `secret_key` | Deployments, in memory, to call the cloud |
| Secret variables | Vault, likewise | Deployments, to hand to the cloud's secret store |
| Database passwords Loomplane generates | Vault, under a key of their own | Deployments, to build the address services get |
| API keys | Keysmith, as hashes | Nobody |
| Passwords | authsome, as bcrypt hashes | Nobody |
| SMTP credentials | Herald, encrypted with a purpose-specific key derived from `secret_key` | The delivery engine only |
| Webhook signing secrets | Relay store wrapper, encrypted with a separate derived key | The signer. One-time response on create or rotation |
| Keyless signing keys | Vault, under an app of their own, encrypted with a key derived from `secret_key` | The issuer, to sign tokens. Only the public halves are published |
| The Hugging Face token | Vault, under `loomplane-ai-credentials`, encrypted with a key of its own derived from `secret_key` | Loomplane, to call Hugging Face, and the engine of a gated model, through a file only it reads |
| Model API keys | Vault, like generated database passwords | Deployments, to hand to the model's guard, its engine and the services that link to it |

Read APIs never return stored credential values. New API keys and webhook signing secrets appear once, when you create or rotate them. The audit trail records key names and the last four characters of an API key, never a value.

Secrets reach a service through the cloud's own secret store: Secret Manager on Cloud Run, Secrets Manager on ECS, sensitive variables on Vercel. Each is readable by that service's runtime identity only. They never pass through Ctrl Plane, which stores what it's given as plain JSON.

Everything depends on `secret_key`. Keep it out of the repository and away from your backups. Losing it loses every credential and secret, and leaking it together with a copy of the database exposes them.

## Keyless signing keys

For a [keyless connection](/docs/clouds/keyless), Loomplane is an OpenID Connect issuer at your public URL, and AWS, Google Cloud or Azure trust the tokens it signs. Nothing about such a connection is a secret you'd store, but the signing keys are, because whoever holds one can act as every keyless connection.

The keys are 2048-bit RSA and sign with RS256. A new one is made every 30 days and published a day before it signs, and the old one stays published for a day after it retires, so a cloud's cached copy always has the key in use. The private halves stay in Vault. Discovery and the JWKS at `/.well-known/` carry public keys only and need no session.

A token lasts 10 minutes and names one connection in its subject, `org:{organization ID}:connection:{connection ID}`, which the cloud's trust has to match exactly. Loomplane signs only when it's handed a ticket the issuer made for that subject and audience, and a credential you paste that's shaped like a keyless handout is refused before it gets that far. Neither a token nor a ticket ever reaches an API response, a log or the audit trail.

## Models

Each model Loomplane deploys runs as two containers: an inference engine and a guard in front of it. The engine listens only on the environment's private network, and its port is never routed. The guard is a Caddy server whose port is the only one that can be. It answers `/health` to anyone, so probes need no key, and refuses every other request with a 401 unless it carries `Authorization: Bearer` and the model's key. Its admin API is off and it has no log directive, so nothing writes a request's `Authorization` header anywhere.

The key is 32 random bytes, base64url, starting `lpm_`, generated per model. Linked services get it as `MODEL_API_KEY`, the guard reads it from its environment, and vLLM and llama.cpp get it too, so they refuse a request without it even from inside the network. The Text Embeddings Inference engine isn't given the key, so for those models the guard is the only check. No API response, page or log shows the key.

The workspace's Hugging Face token is write-only. Saving it checks it with Hugging Face first. Its value goes to Vault, under the `loomplane-ai-credentials` app with a key label (`loomplane/vault ai credentials v1`) no other Vault app shares, and the database keeps only `hf_…` with its last four characters, the account it belongs to and when it was set. It never appears in an API response, a plan, a log, an error or the audit trail, which records the account and the token's revision. Only admins (`ai:manage`) can set or remove it, and removing it is refused while a deployed gated model still downloads with it.

Loomplane sends the token only to the Hugging Face host in `ai.models.huggingface_url`, which must be https unless it's a loopback address. Every redirect off that host is refused, except a file download to Hugging Face's own CDNs, which goes without the token. A pasted repo is read anonymously first. When a gated model deploys, the token goes into the engine's `/etc/loomplane/hf/token` (mode 0400) and nowhere else: not an argument, not a variable a plan records. The engine exports it as `HF_TOKEN` to its own process and downloads from `huggingface.co`. A plan records only the token's revision, so a new token shows as an update. Anyone with Docker access to that server, or who can read Secrets in that namespace on Kubernetes, can read the file.

Models pasted from Hugging Face never run their repository's own code. A registry entry may, but only code reviewed at the commit the entry pins, and nothing a manifest sets can turn it on.

## What runs where

Nothing from a repository runs on a Loomplane machine. Analysis only reads files, in pure Go parsers behind size and file-count limits, in a worker that holds no sessions. Builds run on the clouds' own builders (Cloud Build, CodeBuild, Vercel and so on), in your accounts. Gateways and provider plugins run on your infrastructure, and application traffic never passes through Loomplane.

Provider plugins are trusted with the credentials of the cloud they deploy to, so only configure ones you run or trust. Each needs its own token, and a plugin refuses any request without it.

## Private repositories

For a private repository the worker mints a GitHub App installation token limited to that one repository and to reading its contents, and stores it nowhere. An organization's analyses only use installations that organization connected, and connecting one needs GitHub to confirm the person connecting can see it. See [Private repositories](/docs/guides/private-repositories).

## Recovery email and outgoing notifications

Authsome creates, expires and consumes recovery tokens and revokes existing sessions after a password reset. Loomplane fences redemption with a PostgreSQL advisory lock, because the pinned Authsome otherwise allows simultaneous redemption. Each API admits one reset operation at a time on a dedicated, bounded database connection, so waiting reset requests can't use up the application pool. Conflicting requests return 429.

Recovery links use the configured public URL. Browser pages set `no-referrer`, and reset tokens never enter notification history or audit metadata. Provider error details become a fixed delivery failure message.

Deployment payloads contain allowlisted IDs, status, attempt and an application link, and exclude build logs, variables and raw provider errors. Delayed mail and inbox reads check current project access and organization membership. The outbound HTTP transport blocks private and reserved DNS results, dials only validated addresses, verifies TLS and refuses redirects. [Notifications and webhooks](/docs/guides/notifications-and-webhooks) covers the details.

## How it's tested

- Every route's authorization: an integration test asks for each of an organization's things from another organization, as a developer, as a viewer and with a member's key, and fails on anything that isn't refused.
- Fuzzing for what reads input anyone can send: the manifest parser, repository analysis, the credential parsers and the code that repacks a repository's tarball, which mustn't write a file outside its directory. `make fuzz` runs each for 30 seconds.
- Known vulnerabilities: `make vuln`, and CI on every push, run govulncheck against Loomplane's code and everything it imports. The Go toolchain is pinned in `go.mod` to a release with every standard library fix.
- Static analysis: golangci-lint with gosec, on every push.
- Secrets in tests: integration tests check that secrets reach the cloud's secret store and never a task definition, a list response or the CLI's output.
