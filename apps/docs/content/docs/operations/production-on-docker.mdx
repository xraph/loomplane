---
title: Production on Docker
description: Run Loomplane on one Linux host with Docker Compose, Postgres 17 and Caddy for HTTPS.
---

This stack runs one API and dashboard, one analysis worker, Postgres 17 and Caddy. It tolerates container restarts. A host failure still takes it offline, so keep backups off the host. It isn't a high-availability setup. For that, use [Production on Kubernetes](/docs/operations/production-on-kubernetes).

## Requirements

A Linux host with Docker Engine, Docker Compose 2.24.4 or newer, and a hostname pointed at that host. Open TCP ports 80 and 443 for Caddy's HTTPS certificates and browser traffic. Start with 2 CPU cores, 8 GB of RAM and enough disk for your repositories, database and recovery objects, and measure your workload before you pick something smaller.

## Install

Download the Docker bundle from the GitHub release you want to run, verify its checksum against the release's `SHA256SUMS`, and extract it into `/srv/loomplane`. The bundle holds `compose.yaml`, the `Caddyfile`, `.env.example`, `image.txt` and a README. It pins `.env.example` to the image digest in `image.txt`.

You can also use `deployments/production` from a source checkout. Then choose a published image tag or digest yourself. The example version is a placeholder, not a promise that a release exists.

Run these in the directory that holds `compose.yaml`:

```bash
umask 077
cp .env.example .env
openssl rand -base64 32
openssl rand -hex 32
```

Edit `.env`. Set `LOOMPLANE_IMAGE`, `LOOMPLANE_DOMAIN` (a hostname without `https://` or a path) and `ACME_EMAIL`. Put the first generated value in `LOOMPLANE_SECRET_KEY` and the second in `POSTGRES_PASSWORD`.

The stack sets the public URL to `https://` and your domain. That URL is also the OpenID Connect issuer AWS, Google Cloud and Azure trust for [keyless connections](/docs/clouds/keyless), and they fetch `/.well-known/openid-configuration` and `/.well-known/jwks.json` from it themselves. Caddy passes both through to the API. If the hostname only resolves inside your network, everything else still works, but keyless stays off.

Keep that secret key in your secret manager. Loomplane derives encryption keys from it, and your database backup needs the original key to recover stored credentials. Generate it once, not on each deployment.

The stack passes secrets to containers through environment variables. Protect `.env` with mode 600, restrict Docker access to administrators, and don't paste `docker compose config` or `docker inspect` output into tickets, since both can reveal those values. Validate with `config --quiet`.

```bash
docker compose config --quiet
docker compose pull
docker compose up -d --wait --wait-timeout 240
docker compose ps
```

Open `https://YOUR_HOSTNAME`. Setup needs a one-time token, so get the link first. The API logs it as a `setup is waiting` warning with a `url` field, and `loomplane setup-token` prints the same link:

```bash
docker compose exec loomplane loomplane setup-token
# Finish setup at https://YOUR_HOSTNAME/setup?token=...
```

Open that link, create your account and organization, then connect a repository. Once setup is done the command prints `Setup is complete.` The token comes from `LOOMPLANE_SECRET_KEY`, so it stays the same across restarts. Caddy gets and renews the certificate and forwards WebSocket and SSE traffic to the API. Health and metrics routes are blocked at the public proxy.

If GHCR requires authentication, run `docker login ghcr.io` with a token that can read the package. A newly published package may need its visibility set to public in GitHub before anonymous pulls work.

## Optional push gateway

You can run the push gateway in this stack, behind the same Caddy instance.
Use this if you operate XRaph's gateway or ship your own mobile app build.
The store app needs XRaph's push credentials, so running a gateway with your
own Firebase project or Apple key won't enable push for that app.

Point a second hostname, such as `push.example.com`, at this host. It must
be different from `LOOMPLANE_DOMAIN`. In `.env`, uncomment and set:

```dotenv
COMPOSE_FILE=compose.yaml:compose.push-gateway.yaml
PUSH_GATEWAY_IMAGE=ghcr.io/xraph/loomplane-push-gateway:VERSION
PUSH_GATEWAY_DOMAIN=push.example.com
PUSH_GATEWAY_SEALING_KEY_ID=k202611
```

Choose a published gateway version, preferably pinned by digest. The Docker
bundle includes `compose.push-gateway.yaml` and `Caddyfile.push-gateway`.
`COMPOSE_FILE` keeps the gateway enabled for subsequent `docker compose`
commands, including upgrades on a DigitalOcean install.

Prepare its secret files from the directory containing `compose.yaml`:

```bash
umask 077
mkdir -p secrets
openssl rand -base64 32 > secrets/sealing-key
touch secrets/previous-sealing-key secrets/apns-key.p8
cp /path/to/firebase-service-account.json secrets/fcm-service-account.json
sudo chown 10001:10001 secrets/*
sudo chmod 0400 secrets/*
docker compose config --quiet
docker compose pull
docker compose up -d --wait --wait-timeout 240
```

These commands start an Android gateway. For iOS, copy your Apple `.p8` key
to `secrets/apns-key.p8`, give it the same owner and permissions, and set
both `PUSH_GATEWAY_APNS_KEY_ID` and `PUSH_GATEWAY_APNS_TEAM_ID` in `.env`.
Set `PUSH_GATEWAY_APNS_BUNDLE_ID` when your app uses a different bundle ID.
The Compose option requires a Firebase service-account file even if you
also enable iOS. Keep the empty previous-key and Apple files when unused.

The option sets the API and workers' gateway URL to
`https://PUSH_GATEWAY_DOMAIN` and enables push. Only Caddy publishes ports
80 and 443. On the gateway hostname it exposes `/v1/registrations` and
`/v1/send`, limits request bodies to 64 KB and keeps health checks private.
Your phones and server both need to reach that hostname over HTTPS.

Back up `secrets/` securely alongside `.env`. Never regenerate the sealing
key on restart. Gateway key rotation follows the push notifications guide;
keep `COMPOSE_FILE` enabled for those commands too. After an upgrade,
restart Caddy to reload the mounted configuration. To return to the hosted
gateway, run `docker compose stop push-gateway`, remove `COMPOSE_FILE` from
`.env`, then run `docker compose up -d --remove-orphans` and
`docker compose restart caddy`. The base stack uses
`LOOMPLANE_PUSH_GATEWAY_URL`, which defaults to XRaph's gateway.

## Configuration and storage

The API runs migrations before it becomes healthy, and Compose starts the worker after that check passes. Both run as UID 10001 with a read-only root filesystem, dropped capabilities, a PID limit and a temporary `/tmp`. The API gets a writable artifact volume, and the worker gets its own scratch volume for repository checkouts. Neither container gets the host's Docker socket. Connections to deployment targets use Loomplane's normal credential and approval flow.

| Volume | Contents |
|---|---|
| `postgres-data` | Accounts, credentials, jobs, deployment state and audit records |
| `artifact-data` | Deployment source artifacts and local recovery objects |
| `analysis-work` | The worker's scratch space for repository checkouts |
| `caddy-data` | TLS certificates and Caddy's certificate authority state |
| `caddy-config` | Caddy's saved runtime configuration |

One analysis can unpack up to 2 GiB of source, which is more than the 1 GiB RAM-backed `/tmp`, so checkouts go to `analysis-work` on disk. Keep a few GiB free on the host for it. The worker runs two analyses at once by default. Set `LOOMPLANE_ANALYSIS_CONCURRENCY` in `.env` to change that (the minimum is 1). Each extra analysis needs more disk and more memory, so raise the worker's `mem_limit` in `compose.yaml` along with it. The volume is only scratch space, so you don't need to back it up.

Volume names carry the Compose project prefix `loomplane-production`, so keep that project name stable across upgrades. `docker compose down` keeps the data, and `docker compose down --volumes` deletes it.

Only Caddy publishes host ports. Postgres sits on an internal Docker network. The API and worker also have outbound access for GitHub and cloud APIs. Database traffic stays on this host's Docker network with TLS disabled. If you move Postgres off the host, supply a separate Compose override with a certificate-verified database URL and remove the bundled database dependency.

Set the optional GitHub App variables together when you need private repositories ([Private repositories](/docs/guides/private-repositories)). You can put a multiline PEM in a single-quoted `.env` value, and the webhook secret must match in Loomplane and GitHub.

Email is off until you configure SMTP. Production uses implicit TLS, usually on port 465. Verify delivery with your mail provider before you rely on account recovery.

`LOOMPLANE_BACKUP_URL` can point recovery objects at independent storage. Without it they share the local artifact volume. It doesn't schedule backups of Loomplane's own database.

## Knowledge needs pgvector

The agent's [knowledge](/docs/agents/knowledge) keeps its vectors in Loomplane's own Postgres, so that Postgres needs the pgvector extension. The default `postgres:17-alpine` doesn't have it. To use knowledge, set `POSTGRES_IMAGE` in `.env` to an image that does, such as `pgvector/pgvector:pg17`, and take a [backup](/docs/operations/backing-up-loomplane) first, because that image is Debian-based and an existing data volume can sort text differently. Loomplane creates the extension itself when `ai.enabled` and `ai.knowledge` are both set and the image has it.

Nothing changes without it. With the stock image, Loomplane starts as always and the knowledge switch stays off with a reason.

Backups follow knowledge. A backup taken with knowledge on includes its vector tables, so a restore needs a target with `ai.enabled`, `ai.knowledge` configured, pgvector available and the same `dimensions`. Otherwise the restore refuses, or fails on the dimensions. See [Backing up Loomplane](/docs/operations/backing-up-loomplane#knowledge-and-backups).

## Check health

```bash
docker compose ps
docker compose logs --tail=100 loomplane loomplane-worker
docker compose exec -T loomplane wget -qO- http://127.0.0.1:8780/_/health
docker compose exec -T loomplane-worker wget -qO- http://127.0.0.1:8781/_/health
```

The probes include extension health, so a stalled durable worker can make a container unhealthy even while its HTTP listener answers. The API replaces a durable worker that a database timeout stopped, and turns healthy again once the replacement is polling. Docker's restart policy restarts exited processes but not a running unhealthy container. Alert on unhealthy state, find the cause, and restart the affected service after database or provider access recovers.

Logs rotate at 10 MB per file with five files per container. Send logs and metrics to your monitoring system before you need longer retention, and keep metrics access inside a trusted Docker network. See [Monitoring](/docs/operations/monitoring).
