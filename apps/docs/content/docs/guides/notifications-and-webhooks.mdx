Open **Notifications** to read deployment results, change your deployment email preference and, as an owner or admin, manage signed webhooks.

## Email

Deployment mail goes to the person who started the deployment. Loomplane checks their current organization membership and project access before delivery. Account recovery and verification mail don't follow the deployment preference.

An empty SMTP host disables email. Invitations then show a manual link and say that email is disabled. Production requires implicit SMTP TLS (commonly port 465) and a valid sender address. If the server needs authentication, set the username and password together, and keep the password outside committed configuration.

```bash
export LOOMPLANE_NOTIFICATIONS_SMTP_HOST=smtp.example.com
export LOOMPLANE_NOTIFICATIONS_SMTP_PORT=465
export LOOMPLANE_NOTIFICATIONS_SMTP_TLS=true
export LOOMPLANE_NOTIFICATIONS_SMTP_USERNAME=loomplane
export LOOMPLANE_NOTIFICATIONS_SMTP_PASSWORD=...
export LOOMPLANE_NOTIFICATIONS_FROM=accounts@example.com
```

Set `LOOMPLANE_PUBLIC_URL` to the address people use, because recovery and invitation links are built from it.

### Read mail from a folder

On your own machine you don't need a mail server at all. Point Loomplane at a folder and each email lands there as an `.eml` file you can open in any mail client:

```bash
export LOOMPLANE_NOTIFICATIONS_MAIL_DIR=.forge/mail
```

A relative path is resolved from where the API starts, and `.forge/` is already gitignored. The files hold whole messages, reset and invitation links included, so they're readable by you only. Set this or an SMTP host or a Resend key, not more than one. Production refuses it.

### Test with Mailpit

```bash
docker run --rm --name loomplane-mailpit \
  -p 127.0.0.1:1025:1025 -p 127.0.0.1:8025:8025 \
  axllent/mailpit:v1.30.0
```

Then, before you start the API:

```bash
export LOOMPLANE_NOTIFICATIONS_SMTP_HOST=127.0.0.1
export LOOMPLANE_NOTIFICATIONS_SMTP_PORT=1025
export LOOMPLANE_NOTIFICATIONS_FROM=accounts@example.com
export LOOMPLANE_NOTIFICATIONS_SMTP_TLS=false
```

Open Mailpit at `http://127.0.0.1:8025`.

### What's stored

Herald keeps encrypted SMTP credentials and sanitized delivery outcomes. It doesn't keep recipient addresses, rendered security mail, reset tokens or invitation links in its history. Invitations report `sent`, `disabled` or `failed` on their own, so a delivery failure doesn't discard a valid invitation. Password reset always returns the same public response for known and unknown addresses, so look at sanitized server diagnostics when delivery fails.

## Delivery and retries

A database trigger captures each terminal deployment attempt in the same transaction that writes it. Notification processing retries up to ten times, then marks its health check unhealthy. After you fix the cause, retry processing from the Notifications page. A replay keeps completed channels and Relay's durable acceptance identity, so it doesn't create a second webhook event.

SMTP delivery is at-least-once. A crash after the mail server accepts a message but before Loomplane records success can produce a duplicate.

## Signed webhooks

Owners and admins add endpoints on the Notifications page. An endpoint must be public HTTPS on port 443. Loomplane blocks private and reserved addresses, resolves again when it connects and refuses redirects.

The signing secret appears once, after you create the endpoint or rotate its secret. Store it in your receiver's secret manager. Verify the `X-Relay-Signature` header against the exact request body and `X-Relay-Timestamp`, and apply a tolerance on the timestamp on your side.

Relay owns HTTP retries and the delivery history. The page shows each attempt, its HTTP status and the next retry, and the public API doesn't keep response bodies. A receiver that returns 410 gets its endpoint disabled.

Deployment payloads hold allowlisted IDs, status, attempt and an application link. They leave out build logs, variables and raw provider errors.

## The agent's notices

When the [built-in agent](/docs/agents/built-in-agent) is on, it sends four kinds of notice of its own. Each one lands in the inbox, goes by email and fires one webhook for the workspace, however many people it reaches.

| Webhook type | When | Who gets it |
|---|---|---|
| `agent.request.created` | The agent needs a decision from someone | The people it asks. See [What needs a person](/docs/agents/what-needs-a-person#who-is-asked) |
| `agent.report.created` | The agent opened a report, or one came back or happened again | The members of the project's responsible team (owners and admins when it has none), and the person who started the deployment it's about |
| `agent.budget.created` | The agent stopped investigating because the month's AI budget is spent, and again when it starts | Owners and admins |
| `agent.release.created` | A [release preparation](/docs/agents/release-preparation) ended: promoted by the agent, stale, stopped, blocked or failed | The person who asked, and the members of the project's responsible team (owners and admins when it has none) |

A report or release notice reaches a person only while they have `deployment:read` on its project, and a budget notice only while they have `ai:manage`. The project's team counts only when the project names one. When it doesn't, owners and admins already have it. Repeats of one report send at most one notice an hour. [Watching and reports](/docs/agents/watching-and-reports#notices) has the whole story.

The webhook's body is the notice: `project_id` (empty for a budget notice), `subject_id`, `title`, `body`, `path`, `url` and `need`, the permission a person needs to read it. A release notice's `metadata` carries `release_report_id`, `plan_id` and `state`. A report's `metadata` carries `report_id`, `signal`, `severity` and `environment`, and its title and body have already had the project's known secrets redacted and been through the agent's outbound scan.

### Turn off the agent's email

The agent's mail has a switch of its own, apart from deployment mail. Both are on until you change them, and each person sets their own:

```bash
curl -X PUT -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"agent_email": false}' "$URL/api/v1/notifications/preferences"
```

The body changes only the fields it carries, so this leaves `deployment_email` as it was. `GET /api/v1/notifications/preferences` returns both. With `agent_email` off you still get the agent's notices in the inbox.

## Loomplane Cloud notices

When Loomplane Cloud work for your workspace is stopped, restored or held back, owners and admins get an inbox notice and the workspace gets one webhook. Add these types to an endpoint to hear them.

| Webhook type | When |
|---|---|
| `platform_cloud.suspended.created` | Loomplane Cloud work for the workspace was stopped |
| `platform_cloud.restored.created` | Loomplane Cloud work for the workspace was restored and is starting again |
| `platform_cloud.waiting_capacity.created` | Loomplane Cloud work is waiting for room on a host |

The body is the notice, with the same fields as the agent's notices.
