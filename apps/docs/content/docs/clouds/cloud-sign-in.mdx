title: Connect a cloud by signing in
description: Register an OAuth app once, then connect DigitalOcean with a sign-in instead of a pasted token.
---

A pasted token works, but it's yours to copy, store and rotate. Signing in swaps that for a grant DigitalOcean hands to Loomplane after you approve it, and Loomplane renews the grant on its own. Today DigitalOcean is the one cloud that connects this way.

## Register the OAuth app

You do this once per organization, and you need to be an owner or admin.

<Steps>
<Step>

In Loomplane, open **Settings**, then **Cloud sign-in**. The page shows a callback URL, which is your public URL followed by `/integrations/oauth/callback`. Copy it.

</Step>
<Step>

In DigitalOcean, open **API**, then **OAuth Applications**, and make a new application. Paste the callback URL as the callback. Loomplane asks for the `read write` scope, so the application needs to allow it.

</Step>
<Step>

Copy the application's client ID and client secret back into the Cloud sign-in page and save. The secret is kept encrypted and never shown again, so replace it there if you lose track of it.

</Step>
</Steps>

The callback has to match exactly, down to `https` and the host. If you change `LOOMPLANE_PUBLIC_URL` later, update the application in DigitalOcean too.

## Sign in

Open **Integrations**, choose **DigitalOcean** and pick **Sign in with DigitalOcean**. You approve Loomplane on DigitalOcean's page, pick the team, and land back in Loomplane with the connection ready. The connection belongs to the team you approved, the same as a token does. **Use a token instead** sits underneath if you'd rather paste one.

## Set the app in config instead

If you run Loomplane yourself and want one app for every organization, put it in `config.yaml` or the environment:

```yaml
clouds:
  oauth:
    digitalocean:
      client_id: your-client-id
      client_secret: your-client-secret
```

The same two values read from `LOOMPLANE_DIGITALOCEAN_OAUTH_CLIENT_ID` and `LOOMPLANE_DIGITALOCEAN_OAUTH_CLIENT_SECRET`. Set both or neither, because one without the other stops startup.

Config wins. Once it's set, the settings page shows that the app comes from config and locks it for every organization, so nobody can point their own at something else.

## When a sign-in lapses

DigitalOcean access tokens last 30 days. Loomplane refreshes the grant when it uses it, and again every 6 hours in the background, so a connection in regular use never gets near the end.

A refresh can still be refused. Someone removed the OAuth application, or revoked Loomplane's access from the DigitalOcean account. When that happens the connection shows **Sign-in needed** and nothing deploys through it. Choose **Sign in again** and approve once more. The connection keeps its ID, so your projects and environments carry on without changes.

The person who made the connection and the organization's owners and admins hear about it, in the inbox, by email and as a `connection.sign_in_needed` webhook. You get one notice per lapse, not one per refresh attempt.

## Switch between a token and a sign-in

A token connection can move to a sign-in. Open it, choose **Sign in again** or replace it, and approve on DigitalOcean. The reverse works too: replace a signed-in connection with a token. Either way the ID stays, so nothing that refers to the connection breaks.
