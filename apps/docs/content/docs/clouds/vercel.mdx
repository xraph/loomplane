title: Vercel
description: Connect a Vercel account or team and deploy web apps and static sites.

Loomplane uploads the approved commit to Vercel, which builds it into an immutable deployment. You can deploy a web app or static site on its own, or use Vercel Services to deploy several applications as one project. Resource provisioning and application deployments use separate adapters; see [Vercel resources](https://github.com/xraph/loomplane/blob/main/docs/vercel.md) for storage and Marketplace setup.

## Connect Vercel

Under **Integrations**, choose Vercel and paste an access token. If you deploy to a team, add its team ID (it looks like `team_` followed by letters and digits). Without one, the token deploys to your own account.

Loomplane asks Vercel whose token it is before keeping it. A token that has expired, been revoked or has no access to the team is refused.

## Sign in instead of a token

If a platform owner or admin has set up a Vercel Integration for Loomplane, the connect dialog offers **Sign in with Vercel** first and **Use a token instead** underneath. You install the Integration on Vercel and pick the team or your own account there, so you don't need a team ID. Install it in the same browser you started from. The Integration's token doesn't expire, and Loomplane asks Vercel once a day whether it still works, so an uninstalled Integration asks for a new sign-in. [Connect a cloud by signing in](/docs/clouds/cloud-sign-in) covers making the Integration and what happens when Vercel stops accepting it.

## Use it in a manifest

```yaml
version: 1
services:
  web:
    source: apps/web
    provider: vercel
    needs: [api]
```

A managed resource is only reachable from services on its own cloud, so a Vercel app that needs a Cloud SQL database is a problem on the plan.

## Deploy a monorepo as one project

You can deploy the services in a repository's `vercel.json` together. Choose the frontend's **Settings**, enable **Deploy as one Vercel Services project**, and set the project root to the directory containing that file. Use `.` for the repository root.

Keep one Loomplane manifest entry for the Vercel project. Its `source` selects the frontend found by analysis, so you can still manage its variables and deployment history. The Vercel project root is separate:

```yaml
version: 1
services:
  app:
    source: apps/web
    provider: vercel
    vercel:
      services: true
      root: .
      service_commands:
        web:
          install: pnpm install --frozen-lockfile
          build: pnpm --filter web build
```

Define the applications, routes and private bindings in that root's `vercel.json`:

```json
{
  "services": {
    "web": { "root": "apps/web" },
    "api": { "root": "services/api", "framework": "fastapi" }
  },
  "rewrites": [
    { "source": "/api/(.*)", "destination": { "service": "api" } },
    { "source": "/(.*)", "destination": { "service": "web" } }
  ]
}
```

Remove separate Loomplane entries for the members when you want them deployed only inside this project. Review that plan carefully if those entries already have running deployments: their removal follows Loomplane's normal deletion flow.

The group shares one deployment, environment, URL and rollback history. Retrying resumes that deployment. Variables and resource links belong to the group; configure private member-to-member calls through Vercel bindings. The complete pinned repository is uploaded, including shared packages outside the project root.

Use the current `services` configuration. The older `experimentalServices` format and `vercel.ts` are not supported by this mode. A missing configuration, unknown member command override or top-level build setting stops the deployment. Vercel determines which member frameworks and runtimes it can build.

## Override install and build commands

In a Vercel application's **Settings**, choose an environment and select **Repository default**, **Custom** or **Skip** for each command. In Services mode, enter the exact member name from `vercel.json` before changing its commands.

For a standalone application, the equivalent manifest is:

```yaml
services:
  web:
    source: apps/web
    provider: vercel
    commands:
      install: pnpm install --frozen-lockfile
      build: pnpm build
    environments:
      preview:
        commands:
          build: pnpm build:preview
```

An environment's `commands` or `vercel` block replaces the corresponding base block. Omit a command to keep its repository or provider default. Set it to `""` to skip that step. An empty `commands: {}` restores repository defaults for both commands in that environment.

Overrides change only the uploaded copy of `vercel.json`; your repository is not rewritten. They take effect on the next reviewed deployment and are retained with its configuration for retries and rollback. Keep secrets in Variables because commands appear in manifest history and deployment review. These overrides currently require the Vercel provider.

See [Vercel Services](https://vercel.com/docs/services) and the [service configuration reference](https://vercel.com/docs/services/config-reference) for routing, bindings and runtime options.

## Build logs

Vercel streams its build events, and Loomplane shows them live in the deployment.

## Verified

We ran the full dashboard flow on 18 October 2026 against a real Vercel account with a pinned public Astro static site: saved placements, plan review, approval, build logs, navigating the HTTPS site, a client-side counter and cleanup. After cleanup the account showed no bindings and the old URL returned `DEPLOYMENT_NOT_FOUND`. That qualifies the static-site path. Custom domains and Vercel Services still need live account verification. Services configuration, command overrides and deployment retries are covered by local tests against a simulated provider.
